# コア構文糖はパーサへの直接変更として実装し、汎用マクロ機構は別投資とする

現状の`.mlg`構文は4つの読みにくさを抱えている: `{ }`がif分岐/関数定義の複数節/ブロック/レコードリテラル・パターンの4役を兼ねる多義性、レコード更新構文の欠如（1フィールドの変更に全フィールドの再列挙が必要）、`else if`チェーンの欠如（実体は`cond : List (Bool, {a}) -> a`の呼び心地の悪さ）、型注釈と実装で`def`キーワードが重複する冗長さ。目標としてElixir/Rhombus的な可読性を掲げ、nix-configでの実利用（dogfooding）から得た摩擦を踏まえて再設計する。

当初はこれらをマクロ機構の上に実装する最初のコア構文として設計する方針だったが、パーサ（`lean/Malgo/Parser/CStyle.lean`）の実装を調査した結果、それが成り立たないことが分かった。パーサは手書き再帰下降で字句解析と構文解析が融合し、文法は静的に固定されている。`infix`宣言のように「パーサは平坦に解析し、意味は後続パスで解決する」という先例はあるが、レコード更新のスプレッド構文（`..`）、ガード節（`when`）、文字列補間（文字列リテラル内の埋め込み式）はいずれも、パーサがまだ解釈できない新しい記法そのものを要求する。構文木レベルのマクロ（shrubberyを導入しない方針、既存決定）は既にパーサが解釈できる形の構文にしか意味を後付けできないため、これらの実現手段にならない。

したがって、レコード更新式・単一定義・ガード節・文字列補間の4つ（元の4つの読みにくさに対応する具体的な構文糖）は、Elixirの「核となる読みやすさは組み込みの構文糖として提供し、`defmacro`のような汎用マクロは別の高度な機能として提供する」という前例に倣い、`CStyle.lean`への直接変更として実装する。汎用マクロ機構（構文木レベル、shrubberyなし）は、これら4つの実装手段としてではなく、将来のユーザー拡張向けの別投資として設計・実装する。マクロ展開をコンパイル時にどう実行するかの検討も、この別投資に合わせて先送りする。

## Considered Options

- 当初案「マクロ機構を土台にコア構文を再設計する」: 二重実装を避けられる想定だったが、パーサの具体的な制約（新記法はマクロの入力になれない）により前提が崩れた。
- 「パーサに一般化された拡張ポイントを先に入れ、その上で4つをマクロとして実装する」: `infix`宣言の先例に忠実だが、拡張ポイント自体の設計を先に固める必要があり、実装着手が遅れる。
- 今回選んだ「4つを直接のパーサ変更として先に進め、マクロ機構は別投資」: nix-configに早く価値が届き、Elixirの前例とも整合する。

## Consequences

- レコード更新式は[#422](https://github.com/takoeight0821/malgo/issues/422)のマージ不具合修正とセットで設計する。
- `{ }`の多義性（if分岐・関数の複数節・letブロックが同じ記法を共有する）は、[0003](./0003-if-stays-a-prelude-function.md)の制約の下で、記法をどう視覚的に区別するかの詳細設計を別セッションに残す。
- 4つの実装順序（どれを最初に着手するか）は本ADRの範囲外。
- 「shrubbery相当の字句グルーピング層は導入しない」という方針には、[0004](./0004-optional-brace-indentation.md)で決めた狭い例外（既存キーワード/演算子位置に限るインデント記法）がある。
- マクロ機構の実行基盤（既存の自己ホスト評価器を再利用するか、Lean側に新規実装するか）は本ADRの範囲外とし、別投資として着手する時点で改めて検討する。
