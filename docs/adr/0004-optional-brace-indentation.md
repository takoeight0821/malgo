# インデントを`{ }`の代替記法として、既存のキーワード/演算子位置に限って追加する

`{}`の視覚的な多義性の緩和に加えて、Scala 3の「オプショナルブレース」を参考にしたいという要望があった。Scala 3は`then`/`else`/`match`などの予約キーワードの後でインデントを深くすると、スキャナが仮想的な`<indent>`/`<outdent>`トークンを挿入し、明示的な`{ }`と全く同じ構文木を作る。両方式は完全に互換で、混在もできる。

malgoの`if`はキーワードではなくPrelude関数（[0003](./0003-if-stays-a-prelude-function.md)）なので、インデント発動位置を「サンク引数を取る関数呼び出し全般」まで一般化するのはScala 3より野心的な拡張になる。今回はそこまでは求めず、既にキーワード/演算子でアンカーされている位置（`let`、`with`、節の`->`など、`pStmt`/`pClause`の構文上すでに区切りが明示されている場所）に限ってインデントを`{ }`の代替として使えるようにする。

これは[ADR 0001](./0001-core-syntax-sugar-over-macros.md)で「shrubbery相当の字句グルーピング層は導入しない」とした決定の範囲を狭く超える。ただしRhombus的な汎用mixfix/マクロ拡張の再導入ではなく、Scala 3と同じ、既存の固定文法に対する限定的なスキャナ拡張である。

## Consequences

- `if`/`unless`/`cond`のような、キーワードを持たない関数呼び出しのサンク引数はインデント記法の対象外のまま残る。`{}`の多義性の視覚的区別（if分岐の引数だと分かるようにする方法）は別の手段を要し、詳細設計に持ち越す。
- 字句解析器（`lean/Malgo/Parser/Prim.lean`）にインデント幅を追跡する状態を追加する必要がある。現状は文字列を消費するだけのコンビネータで、この種の状態を持っていない。
