# ゆるい複数引数呼び出しにタプル適用を導入する案の検討

Date: 2026-08-24

## Context

issue #450 (PR #456) の regression 議論の中で、ユーザーから「`f (a, b)` はタプル `(a,b)` を `f` に適用、`f(a, b)` は `a` と `b` を `f` にカリー化適用する」という理解が示された。このセッションで実際に確認した現状仕様（後述）はこれと異なっていたため、ユーザーから新たに「`.field` アクセスの既存の tight/loose 判定機構を、複数引数呼び出しの括弧にも同じ形で適用してはどうか」という設計案が提案された。これはその案を検討するためのドキュメントである。

**現状仕様（実行して確認済み）**: `f(a, b)` と `f (a, b)` は空白の有無に関わらず全く同一で、両方とも `(apply (apply f a) b)`（カリー化2引数適用）になる。`(a, b)` が実際のタプル値になるのは、呼び出し先の直後以外の場所に単独で出現したとき（`let t = (a, b)` など）だけ。

この区別（tight=カリー化, loose=タプル適用）は、旧「Regular」パーサ（2026-03-08削除）を含め、malgoの歴史上一度も実装されたことがないことも別途確認済み。矛盾を「解消した」歴史も存在しない — 単に2025-06-09のC-style導入時からこの仕様のままである。

一方、`.field` アクセスについては既に tight/loose の区別がある（#424/#450由来）: `f (x).field` は loose（`x` 単体に `.field` が結合）、`f(x).field` は tight（呼び出し全体 `f(x)` に結合）。この区別は「直前のトークンとの間に空白/コメントがあったか」で決まる。

## 提案する新方針（検討対象）

- tight `f(a, b)`（空白なし）→ 現状通りカリー化複数引数呼び出し
- loose `f (a, b)`（空白あり、コンマで区切られた2要素以上）→ `(a, b)` をタプル値として構築し、それを単一引数として `f` に一度だけ適用

0引数(`f ()`)・1引数(`f (x)`)の既存挙動は変更対象外。1引数の場合、loose/tightの違いは既に「後続の `.field` がどこに結合するか」だけの問題で、呼び出し自体の値の意味は変わらない — #424/#450 の対象そのままで、これは維持する。

## 調査結果

3並列の Explore エージェントによる全面調査を行った。

### 1. 既存コードでの使用実態（影響範囲はゼロ）

`runtime/malgo/`（`Builtin.mlg`/`Prelude.mlg`/`compiler/*.mlg`）・`examples/malgo/`・`test/testcases/`（`malgo/`/`scheme-only/`/`forth/`）・`bench/fixtures/` を全面的に検索した結果、**ゆるい複数引数呼び出しは実コードに一件も存在しない**。全て tight な `f(a, b)` の形でのみ書かれている（`CStyleApply.mlg`/`CStyleDataDef.mlg`/`CStyleTypeSynonym.mlg` を含む、C-style構文専用のテストファイル群も同様）。

型レベル(`pTyCStyleTuple`/`pTyApp`)・パターンレベル(`pConP` のC-style部分、`data Map(k, v)` のような宣言)には、そもそも tight/loose 判定機構自体が存在しない（#424 は expression のみが対象だった）。新方針も expression のみに限定するなら、これは既存の非対称性と整合し、新たな非対称を生まない。

### 2. 既存テストへの影響（実質1箇所のみ）

変更が必要なのは `lean/Test/Main.lean:814-816`（"does not disturb a two-argument call written with a space: `f (a, b)`" が `(apply (apply f a) b)` を pin している）のみ。ここを `(apply f (tuple a b))` 相当に変更する必要がある。隣接する811-813行目（tight版、`f(a,b)`）は変更不要。

`.golden/Malgo.Parser/` の20ケース、`CStyleApply.mlg` 等の専用テスト、Zig/Scheme backend の golden 群はいずれも tight呼び出しのみを使っているか、パース済みIRを消費するだけなので無影響。

### 3. self-hosted parser の現状

`runtime/malgo/compiler/{Lexer,Parser}.mlg` には**現在、空白追跡が一切存在しない**（ファイル誕生時（#342, `a93008e6`）からの全コミットを確認したが、一度も追加されていない）。現在別エージェントが進行中の #450/#456 の修正が、self-hosted lexer に初めて tight/loose 追跡を導入する。それが着地すれば、新方針を拡張する土台ができることになる。

`parseAppRest` の C-style呼び出し判定(`canCStyleCall`)は `ExVar`/`ExField` のどちらにも同一に効く — つまり**関数呼び出しとコンストラクタ呼び出しを構文段階では区別していない**。これが次の、最も重要な調査結果に直結する。

### 4. `#c-style-apply` プラグマ・`malgo2025` との関係

`#c-style-apply` は現在完全に no-op（許可リストにあるだけで、どこからも参照されない死んだフラグ）。今回の変更に絡める必要性・妥当性はない。`malgo2025` は codata脱糖(`Elaborate.pass`)のみに関与し、呼び出し構文とは無関係。

### 5. 決定的な複雑化要因: データコンストラクタとの衝突

今回の調査で見つかった**最大の設計上の障害**がこれである。

- パース段階では、関数呼び出しとコンストラクタ呼び出しは構文的に区別されない（`canCStyleCall` は大文字始まりかどうかを判定していない）。コンストラクタかどうかが確定するのは Rename/型検査より後。
- `ToFun.fromConstructor` は全てのデータコンストラクタを「1引数ずつのネストしたカリー化ラムダ」としてコンパイルし、`SaturateCtor.trySaturate`/`unrollSpine` はその「1引数ずつの適用の連鎖」を辿って、引数の個数がコンストラクタの arity と一致したときだけ `Fun.Construct` に静的にインライン化する。
- 新方針を無条件に（関数・コンストラクタ問わず）適用すると、`Cons (x, xs)`（loose）は「タプル `(x, xs)` を `Cons` に1回だけ適用」という形になり、`args.length` は1、要求される arity は2 — `trySaturate` はこれを認識できず、実行時には「1引数しかもらっていない、部分適用されたコンストラクタ」として扱われてしまう（コンパイルは通っても、意図通りには動かない）。
- パース段階でコンストラクタ呼び出しだけ「常にtight相当（常にカリー化）」として例外扱いすることは実装可能だが、それは「大文字始まり識別子は常にカリー化」という**構文規則**として言語仕様に格上げする必要があり、現在は単なる命名慣習でしかないものを文法上の区別に変えることになる。

## 検討した代替案

1. **（推奨）現状維持** — 呼び出し構文自体は変えず、タプルを明示的に1引数として渡したい場合は `f((a, b))` と書く現在の方法を維持する。理由: 実コードでの需要がゼロ（調査で確認済み）であり、コンストラクタ飽和との衝突という実質的なコストに対して、解決すべき実際の問題が存在しない。#456 の修正はこの現状（一貫した既存仕様）に self-hosted parser を合わせるだけで完結する。
2. **新方針を expression レベルの関数呼び出しのみに限定し、大文字始まり識別子（コンストラクタ）は構文規則として除外する** — 実装は可能。ただし「大文字始まりは常にカリー化」という新たな文法規則を追加することになり、現状「単なる命名慣習」だったものを文法に格上げする副作用がある。`SaturateCtor` への変更は不要。
3. **新方針を無条件に適用し、`SaturateCtor`/`ToFun` にタプル引数の展開ロジックを追加する** — 最も一般的だが最も侵襲的。「飽和したコンストラクタ呼び出しが、arity と一致するタプル1個を受け取った場合はそれを展開する」という新しい飽和規則が必要。この場合、`Cons (x, xs)` と `Cons(x, xs)` はコンパイル後に同じIRになるべきかどうかも決めないといけない — 同じにするなら「タプル適用」と「カリー化適用」の意味的な違いも消えてしまい、そもそもの提案の目的（2つの意味を区別すること）と矛盾しかねない。

## 推奨

**今回は見送り、代替案1（現状維持）を推奨する。** 実コードでの需要がゼロであることが調査で確定しており、導入する場合はコンストラクタ飽和との整合性という実質的なコストが発生する（代替案2は新しい文法規則の追加、代替案3は提案自体の目的と矛盾しかねない）。現在進行中の #450/#456 の修正は、この「現状維持」の方針と完全に整合する — self-hosted parser を、既に確立されている Lean oracle の仕様に合わせるだけで良く、この設計判断を待つ必要はない。

もし将来、実際に「関数にタプルを1引数として渡したい」という具体的な需要（例: #440 のような外部インポート機能で、複数の設定値をまとめて渡すAPIなど）が出てきたら、代替案2（コンストラクタを構文的に除外）が最も現実的な出発点になる。

## Risks

| Risk | Mitigation |
|---|---|
| コンストラクタ呼び出しとの衝突（本ドキュメントの核心的な発見） | 代替案2で構文的に除外する、または今回は実施しない |
| 実需要が不明なまま複雑さを追加してしまう | 今回は見送り、具体的な需要が出てから再検討する |
| self-hosted parser と Lean oracle の実装がズレる | #456 と同様、両実装を一つのPRで同時に変更し、goldenの比較で検証する |
| 「大文字始まり=コンストラクタ」が構文規則になることで、将来大文字始まりの通常関数を書けなくする/驚きを生む | 代替案2を選ぶ場合、この制約をドキュメントで明示し、既存コードに大文字始まり関数が実在しないか事前に確認する |
