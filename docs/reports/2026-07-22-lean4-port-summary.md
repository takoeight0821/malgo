# Malgo の Lean 4 移植: M0からM9までの総括

## 背景と目的

Malgo は Haskell で書かれたインタプリタを持つ静的型付き関数型言語である。
この移植は、パーサからそれぞれのバックエンド（Eval/Scheme/Zig）、クエリベースのコンパイル基盤、リンタ、MET デバッグトレーサまで、Haskell 実装と対をなす第二の実装を Lean 4 で作る作業である。
計画は M0 から M9 までの十段階に分けられ、2026年7月19日にすべて完了した。
Haskell 実装は、コミット済みのゴールデンファイル一式、自己ホスト型コンパイラを用いた負荷試験、`scripts/zig-golden.sh` の両方に対して、Lean 実装とともに引き続き意味論の基準であり続ける。

## M0からM4: コア・パイプラインの移植

パーサ、名前解決、型推論（省略可能）、Fun IR から Core IR、Flat IR、Join IR へ至る変換までの中核パイプラインを移植した段階である。
2026年7月19日時点で `lake test` は434件のゴールデンと94件の型推論テストにすべて通過し、`scripts/lean-parity.sh` は評価結果とビッグステップ評価の両方で292件、8件のエラーモードに一致した。
自己ホスト型コンパイラを用いた負荷試験（レベル1で73件、レベル2のメタ循環評価で5件）も通過している。

この段階で、二つの並行エージェント作業が意味論の乖離に近づいた事例が記録されている。
一つは `Query.Engine.buildDepsEnv` の衝突検出である。
あるテストケースの失敗を解消するため、本来は衝突を検出すべき関数を、無条件に左側を優先する統合へ書き換える修正が提案された。
これは Haskell 版のオラクルから静かに乖離する変更であり、実際に Haskell バイナリを動かして確認した結果、Prelude が Builtin を再エクスポートする構造に起因する、Haskell 側にも存在する（潜在的な）挙動であることが分かった。
正しい修正は、Haskell 自身のテストハーネスが使っている寛容な統合関数（`Test/Main.lean` の `buildDepsEnvLenient`）を、対応する箇所にだけ追加することだった。
テストの失敗を、意味論を緩めることで通過させるのではなく、実際の Haskell バイナリの挙動を確認したうえで対応した。

もう一つは、M1 のレビュー時に「ビッグステップ評価はまだ移植されていない」という理由で追加した CLI 上のガードが、実際にビッグステップ評価が実装された後も取り除かれず、`compileAndEval` が評価モードを一切見ずに動作し続けていた事例である。
ゴールデンテストはこれを検出せず、`scripts/lean-parity.sh` によるオラクル比較で初めて発覚した。
ある段階で暫定的に追加した「未実装」の防御コードは、対応する機能が後の段階で実装された時点で見直す必要がある。

## M5: Zig バックエンド

Perceus 参照カウント方式による、ネイティブ実行ファイルを生成するバックエンドを移植した段階である。
Normalize、ClosureConv、Peephole、Perceus、Reuse、RcCheck、Emit、ツールチェイン連携、CLI 配線を三つの並行エージェントで分担した。
`lake build` は108ジョブすべてが成功し、`scripts/zig-golden.sh` によるゴールデンテストの全件走査（73件）でコンパイル失敗・実行失敗・不一致・タイムアウト・メモリリークがいずれもゼロだった。

境界レビューで三件の修正を行った。
最も本質的なのは、外部プロセス呼び出しの失敗検出方法である。
`zig` コマンドが存在しない場合の検出を、当初は `IO.Process.output` の例外捕捉で行っていたが、これは Haskell の `readProcessWithExitCode` の例外送出に基づく発想をそのまま持ち込んだものだった。
実際に確認すると、Lean の `IO.Process.output` はコマンドが存在しない場合でも `IO.Error` を送出せず、終了コードが非ゼロの `.ok` を返すだけだった。
この事実は、実際にコマンドを実行して確かめて初めて分かった。
修正は、`$PATH` を手動で走査する `findOnPath` によって、プロセスを起動する前に存在確認を行う方式に変更し、Haskell の `findExecutable` を先に呼ぶ制御フローに合わせた。
Lean の標準ライブラリ関数が、置き換え元の Haskell 関数と同じ形でエラーを伝えるとは限らない。
実際に両方の分岐を動かして確認する必要がある。

## M6: リンタと開発者向けツール

`malgo lint` の5個のスタイルルール、IR 全体を描画する `Debug/PrettyIR.lean`、Myers の差分アルゴリズムを再実装した `Debug/DiffView.lean` を移植した段階である。

この段階の中心的な発見は、レイアウトエンジン `Doc.lean` の移植で起きた。
`Malgo.Prelude` に既にあった `Pretty` 型クラスは単なる文字列変換であり、`nest`/`group`/`layoutSmart` を備えた本物のレイアウトエンジンではなかった。
このため `Doc.lean` は、ピン留めされた `prettyprinter-1.7.2` の実際のソースコードから一行ずつ移植する形で新規に書いた。

移植の過程で、単なる誤答ではなく、数分間ハングするという形の不具合が二件見つかった。
一つは `changesUponFlattening` の `Cat` の場合分けである。
Haskell の `case (f x, f y) of (NeverFlat, _) -> NeverFlat; ...` は遅延評価によるタプルマッチであり、第一要素が `NeverFlat` であれば第二要素は評価されない。
これをそのまま Lean の `match f x, f y with` へ移すと、正格評価のため両方が必ず評価され、早期終了のつもりだった分岐が毎回 `y` への全再帰を引き起こしていた。
`x` の側から先にマッチする形に書き直すことで解決した。

より深刻なのは `best` 関数の `Union` の場合分けである。
Haskell 版は、二つのレイアウト候補を `let` で束縛したうえで、実際に必要な分だけしか強制評価しない。
候補のどちらが採用されるかを決める `fits`/`selectNicer` は、典型的には最初の一行しか強制評価せず、採用されなかった側の残りは一切具体化されない。
この省略は遅延評価によって暗黙に成り立っている。
Lean へ正格評価のまま移植すると、両方の候補をあらゆる入れ子の深さで完全に構築してしまい、`group` の入れ子が深くなるにつれて計算量が指数的に増大する。
実際に、162行の Zig IR トレースの描画が数分間終わらないことで確認した。
修正は、`SimpleDocStream` の再帰的な後続部分を `Thunk` として持たせ、`best` が継続を計算する箇所を `Thunk.mk` で包むことで、Haskell の遅延評価が持っていた打ち切りを明示的に復元する形で行った。
修正後は同じ162行のトレースが約1.3秒で描画され、89件のゴールデンテスト全体も約14秒で完了する。

遅延評価に依存した Haskell のアルゴリズムを移植するときは、その計算量自体が遅延評価に支えられていないかを事前に確認する必要がある。
支えられているなら、型が合うように置き換えるだけでは足りず、`Thunk` による明示的な遅延化か、制御フローの再構成が要る。
このクラスの不具合は誤った出力ではなくハングとして現れるため、ゴールデンテストだけでは検出できない。

## M7: LSP サーバ

`malgo-lsp`（標準入出力上で動く、外部ライブラリに頼らない最小限の LSP サーバ）を移植した段階である。
`initialize`/`initialized`/`shutdown`/`exit` と、`textDocument/{didOpen,didChange,didClose,hover}` を実装し、診断はパースと名前解決の失敗からのみ生成する。

この段階で追加した `Malgo.Monad.runCatching` は、LSP に限らず再利用できる部品である。
既存の `MalgoM.run` は `CompileError` を文字列化した `IO.userError` へ潰してしまうため、診断に必要な位置情報（`range?`）が失われる。
`EIO.toBaseIO`（元のエラー型を保ったまま `EIO` を解く、Lean core が提供する原始的な変換）を使い、構造化されたエラーを保持したまま結果を取り出す関数を `run` の姉妹として追加した。

境界レビューでは、JSON パーサの数値表記（`5.`、`1e`、`1.e5` のような不完全な形式を受理してしまっていた不具合）と、サロゲートペアで表現された絵文字などの文字が `Char.ofNat` の制約によって NUL バイト二つに壊れていた不具合を修正した。
`malgo-lsp` には Haskell 側の対応するテストが一つも存在せず、`Test/LspSession.lean`（実際のバイナリを起動し、初期化から `didOpen`、診断の受信、終了までを一通り動かす統合テスト）は比較対象を持たないまま新規に書いた。

## M8: MET デバッグトレーサ

Haskell 版の `app/met` は `servant` によるライブラリサーバだったが、Lean の標準ライブラリにはネットワーク機能が乏しいため、計画の時点で「サーバを持たない」方針が決まっていた。
コンパイルパイプライン全体のトレースを、一つの自己完結した静的 HTML ファイルへ描画する `malgo debug-trace` サブコマンドとして実装した。
ページ遷移や差分ビューの切り替えは、サーバとの往復ではなく、ページ内の少量の JavaScript による表示切り替えで行う。

## M9: 総括作業

計画全体の最終段階として、`PORTING.md`（Haskell と Lean のファイル対応表と、Haskell 実装を引退させるための基準）を作成した。
引退の基準は、CI が最低一週間グリーンであり続けること、パリティ確認が連続二回成功すること、性能予算について合意があること、実際の利用実績があることの四点であり、いずれもまだ満たされていない。
`bench/lean-vs-haskell.sh` による実行時間比較では、評価とコンパイルのいずれも1.1倍程度の差に収まり、これは誤差の範囲と言える。
この比較の過程で、`fib(18)` 以上を `--opt release-fast` でコンパイルした実行ファイルがセグメンテーション違反を起こすという、Zig バックエンドの既存の不具合を見つけた。
Haskell 版とLean 版の両方でこの不具合が再現することを確認したうえで、この移植の範囲外として記録するにとどめた。

## 全体を通じた教訓

フルレビューの手順を経ることで、二件の回帰を実際に防いだ。
M2 のレビューでは、ドキュメンテーションコメントを直す作業のついでに紛れ込んだ、依存関係のリンク順序に関する回帰を検出した。
M3 のレビューでは、Haskell の `env <> Map.fromList freshVars` が持つ左辺優先の統合を、最初の Lean 版が無条件の上書きへ反転させていた不具合を検出した。
どちらも狭いテストケースでしか顕在化せず、単に「テストが通る」ことの確認だけでは見逃していた種類の不具合である。

Lean 4.32 特有の落とし穴も複数回記録している。
`String.drop`/`dropWhile`/`dropEnd` が `String.Slice` を返すため `toString` で包む必要があること、`meta` が予約語であること、ハイフンを含む Lake の実行ファイル名がテストドライバとして解決されないこと、再帰型に `List`/`Option` を含むフィールドがあると `deriving Ord` が失敗すること、`where` 節の中の `partial def` が解決できない型クラスメタ変数を引き起こすことがあることなどである。
これらはいずれも、コードを読むだけでは気付きにくく、実際にビルドして初めて分かる類の制約である。

M9 完了の時点で、Haskell 実装を廃止する条件は満たされていない。
この移植は Haskell 実装の置き換えではなく、並行して保守される第二の実装として位置づけられている。
issue #359 以降の証明導入の作業は、この総括の後に続く独立した取り組みであり、別のレポートにまとめている。
